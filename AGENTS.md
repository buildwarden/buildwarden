# AGENTS.md — BuildWarden Developer Context

## What This Project Is

BuildWarden is a build-time network auditing platform. It runs builds across four
drivers (container, qemu, vz, hyperv), all sharing one model: a **relay** is the
sole network path for the build environment and records every request to a
cryptographically-signed ledger, while a host-side **collector** is the relay's
single output path and the source of its build inputs.

- **Relay** — An ephemeral HTTPS MITM proxy that intercepts all build traffic,
  records it to the ledger, and serves as DNS resolver for the build environment.
  It keeps no build state on disk and mounts nothing: it boots unconfigured,
  waits for a claim, then streams every output to (and pulls every input from)
  the collector. Also handles artifact ingestion via `POST http://artifacts/<name>`.
- **Build environment** — A container (container driver) or VM (qemu/vz/hyperv)
  where the build runs, network-isolated so it can only reach the relay.

The output is a tamper-evident binary ledger of all network I/O during the build.

## Running

```sh
# Autodetects runtime (finch > docker > podman)
./warden build examples/Dockerfile.simple

# Explicit runtime
./warden build --runtime docker examples/Dockerfile.simple

# Interactive shell in build environment
./warden shell ./examples
```

Configuration via `warden.toml` or `~/.config/warden/config.toml`.

## Key Design Decisions

### Cryptographic Architecture (Two-Key Design)
- **MITM CA** — RSA-2048, generated by the relay at startup. Used solely for TLS interception. Private key NEVER leaves the relay container's memory.
- **Ledger Signing** — Ed25519, generated by the relay at startup. Used for signing ledger entries (~50k signs/sec). Public key embedded in ledger header.

### Orchestrator ↔ Relay Flow (claim + tunnel + collector)
1. Orchestrator starts a collector serving the build script and context, and receiving outputs
2. Orchestrator boots the relay, unconfigured, listening for one claim on port 8301
3. Orchestrator opens a tunnel (`POST /v1/tunnel`) and serves the collector to the relay over it as HTTP/2 (host-initiated; the relay never dials the host)
4. Orchestrator claims the relay (`POST /v1/claim`) with the build config (collector URL + token, capture mode, upstream CAs, optional environment record)
5. Relay returns its identity: ephemeral MITM CA cert (written to `<output>/ca.cert.pem`) and the ledger's Ed25519 public key; the claim listener then closes
6. Orchestrator runs extensions (inject CA into the build environment trust store), starts the build environment, applies network isolation
7. Build runs with all traffic flowing through the relay; outputs stream to the collector, and the ledger is flushed before `/v1/complete`

### Binary Ledger Format
- Magic: `BLDL` + version byte (0x01)
- Self-describing header: signature scheme, sizes, public key
- Record types: open, checkpoint, close, artifact
- Payload direction encoded in signed int64 (positive=in, negative=out)
- CBOR metadata (not signed, freely redactable)

### Artifact Endpoint
- DNS resolves `artifacts` hostname to relay IP (10.0.87.2)
- `POST http://artifacts/<name>` is intercepted by the relay
- Body streamed to `payloads/<sha256>`, symlink at `artifacts/<name>`
- Recorded in ledger with dedicated `artifact` record type

### Fail early, say what to do
A project standard (full text in DEVELOPING.md). A failure with a clear cause, such as a missing root or Administrator right, an unprepared image, an absent tool, a stopped runtime or a bad flag, returns `driver.Fixable(fix, ...)` naming the exact remedy. warden prints `To fix: ...` and no file-a-bug link. Check for it before any slow or irreversible step (download, restore, VM boot, network standup) whenever the check is cheap relative to a successful run. Recognized opaque platform errors are mapped at the call site.

## Extension System
Extensions implement `BeforeBuild(env *CtrEnv) error` and optionally `Env() map[string]string`. They run on the host before the build starts and can write files to the staged `/.warden` tree (`ExtensionContext.WardenDir`, in the build's private work dir, never the build context; copied into the build container as `/.warden`) and scripts to its `ext.d/` (exec'd inside the build container).

## Container Runtime Abstraction
Uses `github.com/lesiw/ctrctl` which wraps docker/finch/podman CLI. Runtime is autodetected or configured via `warden.toml` / `--runtime` flag.

## Finch VM Configuration
For heavy builds (PyTorch), the finch VM needs:
```yaml
# ~/.finch/finch.yaml
cpus: 6
memory: 16GiB
datadisk: 150GiB
```
