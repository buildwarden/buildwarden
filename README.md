# `workflow`: BuildWarden's feature-queue state

This orphan branch shares no history with `main`. It holds the bookkeeping of
the development process in
[`docs/development/process.md`](https://github.com/buildwarden/buildwarden/blob/main/docs/development/process.md):
which features are queued, what phase each is in, who holds which step, what is
blocked on a human or a native host, and what each daily run did. It lives here,
not on `main`, so the high-churn state stays out of the code history (FLOW-03).

The rules are in `docs/development/`; the procedures that read and write this
branch are the skills under `.claude/skills/` on `main` (`workflow-tick`,
`workflow-human`, `workflow-native`, `workflow-intake`). Nothing here is
hand-edited when a `wf` command can make the change.

## Layout

| Path | What |
|---|---|
| `QUEUE.md` | Generated by `wf` whenever it saves state, validates or commits: what needs Jeff, what is active and at which phase (with each item's lead), the Workers (each machine's host names, last run, the items it leads and the leases it holds), how the open items relate, what waits on a host, and the backlog. Done items are left out; `wf status -all` lists them for a retrospective (FLOW-13). Never hand-edited; `wf status -md` prints the same. |
| `config.yaml` | Loop settings: the repository, the `repositories` an item may name (each with its trunk and, once adopted, its profile file), the priority gate, run budget, FLOW-05 limits, lease length, runaway factor. |
| `areas.yaml` | The area map of `config.yaml`'s `repository` (FLOW-05, PROFILE-01): its areas, their paths and modes, `reaches`, `implies` and `written_seams`. Changed only on Jeff's word, in an attended session (`wf validate -areas`, then `wf commit -worker human/<name>`, which refuses any other worker). Absent: the repository is one exclusive area. `wf areas -list` prints it; `wf areas -check` compares it with `main`. |
| `main.yaml` | What a session last read about `main`, written by `wf main` and `wf areas -check`: the head, its CI (`green`, `red`, `pending`, `red_since`, a failing run, the follow-up filed for it), whether GitHub requires an up-to-date branch (`up_to_date`), and the map's comparison with that head. On a push conflict `wf commit` keeps the remote's file. |
| `repos/<owner>/<name>/areas.yaml`, `repos/<owner>/<name>/main.yaml` | The same two files for another repository in `repositories`: its area map (absent: one exclusive area) and its trunk as `wf main -repository <owner>/<name>` and `wf areas -check -repository <owner>/<name>` last recorded it. The queue's own repository keeps the top-level `areas.yaml` and `main.yaml`. |
| `queue/<feature>.yaml` | One file per feature: its state, steps, budget, questions and history. |
| `queue/done/<feature>.yaml` | Done items, without a priority, read for `follows` and `wf status -all`. Created by `wf migrate -done` (queue-positions). |
| `hosts.yaml` | Native machines, the host names each one's scheduled session serves, and the `repositories` it takes steps for (FLOW-04, FLOW-09); read by `wf gate`, `wf next` and `wf validate`. |
| `backlog/native-gaps.yaml` | Validation deferred by merged designs, per host (FLOW-09, TEST-03). |
| `digest/<YYYY-MM-DD>/<UTC start>-<worker>.md` | One file per run (`20261114T105653Z-cloud.md`), dated by the Pacific date of the run's start: what moved, what is blocked on Jeff, what waits on a host, what was spent (FLOW-13, LOOP-06). |
| `digest/<YYYY-MM-DD>.md` | The day's page, built by `wf digest` (and by `wf commit`) from that day's directory in file-name order. Generated; never hand-edited. |
| `reports/<feature>/<sha12>.{md,json}` | The behavioral linter's tier-2 report for a branch head (LINT-04, LINT-05), report-only (LINT-07). |
| `native/<host>/<date>/` | Logs a native session attaches to a failure. |
| `native/status/<machine>.yaml` | Each machine's last scheduled run, written by `native-tick.sh` from an EXIT trap: `machine`, `last_run` (UTC), `outcome` (`worked`, `idle`, `skipped`, `failed`), a one-line `reason`, and `since` (when this outcome began). Pushed only when the outcome or reason changes, or the last push is a day old. Never log contents (FLOW-18). Checked by `wf validate`. |

## `config.yaml`

```yaml
priority_confirmed: false   # unattended runs do nothing until the human confirms the order
repository: buildwarden/buildwarden  # whose gates wf runs and whose map areas.yaml is; no default,
                            # and an item with repos fails wf validate while it is unset
repositories:               # every repository an item may name (LOOP-01, PROFILE-01)
  - name: buildwarden/buildwarden          # owner/name, listed once
    trunk: main                            # required; wf reads a trunk here only
    profile: docs/development/loop-profile.yaml  # the profile file, in that repository; absent: not adopted
  - name: buildwarden/buildwarden-specs    # not adopted: no profile
    trunk: main
run_budget: {steps: 8}      # steps one run may take; calibrate against /usage
native_budget: {steps: 8}   # steps one scheduled native session may take (FLOW-13);
                            # unset falls back to run_budget; `wf budget -native`
limits:
  in_progress: 5            # FLOW-05: features in progress; process items not counted; 5 when unset
  alters_relationships: 1   # FLOW-05: features holding an alters_relationships slot; 1 when unset
  waiting_on_human: 8       # FLOW-05: no queued feature starts while this many items wait on
                            # the human; 8 when unset
lease_minutes: 120          # FLOW-04: a cloud or human claim's lease
host_lease_minutes: 1200    # FLOW-04: a native machine's claim's lease, refreshed by wf renew;
                            # 0 or unset is 1200 (loop-native-lead)
runaway_factor: 2           # FLOW-13: escalate at this multiple of the step estimate
```

Every limit is 1 or more; one written below 1 fails `wf validate`.

`wf validate` fails an entry with no `trunk`, a name listed twice or not in
`owner/name` form, a queue whose own `repository` has no entry, and an item
naming a repository with no entry; an absent entry is never read as a default.
An entry gains its `profile` only after the pull request that adopts the
repository has merged, on Jeff's word. Until then the repository has no fast
gate, no reference documents and no rule or machinery paths; its branch,
area, trunk and pull-request checks still run. A profile file whose `trunk`
differs from its entry's fails every check that reads it, naming both.

### The profile file

The entries of a repository's profile (PROFILE-01) that the loop's tools read
(LOOP-01), at the path its `repositories` entry names. A change to it is a
change to the profile, so the file is always a rule path. This repository's
is `docs/development/loop-profile.yaml`:

```yaml
version: 1                    # an unknown version fails every check that reads the file
component: buildwarden
trunk: main                   # must equal the config.yaml entry's
branch: feat/{item}
designs: {dir: docs/design, template: docs/design/TEMPLATE.md}
fast_gate: [[make, lint], [make, test]]   # each run in the checkout, must exit 0 (FLOW-03, FLOW-17)
impact:                       # front-matter keys added to the loop's eight, and their values
  keys: [drivers, surfaces, security_boundary, tier2_gaps]
  values: {security_boundary: [none, host-env, env-relay, env-beyond]}
reference_docs:
  implement: [docs/]          # changed in Implement when the design declares surfaces (UX-01)
  guides: [docs/book/src/guide/, docs/book/src/getting-started/, examples/, README.md]
rules:
  dir: docs/development       # LINT-01's files
  paths: [...]                # rule paths for the clearance, read at the branch's merge base
  machinery: [.claude/, tools/workflow/]
  rule_jobs: '<regexp>'       # CI jobs that enforce rules
  index: tools/tier1/rules.yaml   # LINT-01's rule-to-check map; absent: rule IDs only
areas: {edges: [tools/tier1/area-edges.sh]}   # what wf areas -check compares the map with
toolchain_check: [go, version]
native:
  prepare: {windows-hyperv: [[tools/relay-vm/hyperv/refresh-cache.sh]]}         # before a native session
  check: {windows-hyperv: [[tools/relay-vm/hyperv/refresh-cache.sh, --check]]}  # by the install script (LOOP-05)
```

A key absent from the file is `none` (no fast gate, no reference documents, no
machinery), never this repository's value. An unknown key, an unknown
`version` or a file `wf` cannot parse fails every check that reads it, naming
the file. `wf rules -profile FILE` runs the generic rule checks against it.

## `queue/<feature>.yaml`

```yaml
feature: container-inputs        # == file name
title: Record container inputs under inputs/ (ORCH-02)
priority: 2                      # the position in FLOW-05's order, 1 first; wf renumbers it; none once done
kind: feature                    # feature (default, omitted) | process (FLOW-03)
holds: []                        # process only: affinity patterns held while in progress
follows: build-link-subnet       # optional (FLOW-05, FLOW-09): the item this one fixes; a fix (class 3), offered once that item is done
lead: host:windows-hyperv        # optional, a feature only (FLOW-04, FLOW-09): the host name whose machines take
                                 #   its cloud steps of phases 0-5; any worker may set or clear it (wf lead,
                                 #   wf new -lead), each change a history line
urgent: human/jeff               # optional (FLOW-05): a security fix that follows no item, marked by a human
                                 #   (wf new -urgent, wf urgent [-clear]); it starts past the waiting limit
status: in_progress              # queued | in_progress | done
round: feature                   # feature | process | tracked (FLOW-03); parallel and merge only
                                 #   on items finished before workflow-streamline
phase: 1                         # FLOW-03 phase: 0 branch-setup .. 8 close; process 1..4
design: docs/design/container-inputs.md
branch: feat/container-inputs
repos: [buildwarden/buildwarden] # optional: the repositories it works in, home first; absent: config.yaml's repository
areas: [driver/hyperv, book]     # optional: names from areas.yaml; absent: undeclared, collides with every
                                 #   item in its repositories; [] declared, changes nothing but its design
seams: [relay-claim]             # optional: the design's seams (FLOW-02)
rules_changed: [GLOBAL-08]       # optional: the rule IDs of the design's rule_changes (FLOW-14)
declared: 4c1d9e2                # the branch commit whose design wf declare last copied; absent: never declared
adopts: {consumable: buildwarden-relay, version: v0.3.0}  # optional: a reconciliation item (LOOP-07)
collides_with: [other-item]      # optional: the human's word that they collide (wf relate, human only)
alters_relationships: null       # null until Design decides (FLOW-02)
design_review: required          # unset until Design decides: required | skip (FLOW-19)
source: where the item came from
pr: {number: 0, ci: pending, head: 0a1b2c3}  # set by Publish (f6-open-pr, x2-implement) and each refresh:
                                 #   ci pending | green | red, read for the commit head records
work:                            # optional: one entry per repository in repos after the home, written by
                                 #   wf declare from the design's repos and merge_first
  - repo: buildwarden/buildwarden-specs
    branch: feat/container-inputs  # the home's branch name
    first: true                  # in merge_first: merges in Publish, confirmed by f6-merged-<n>;
                                 #   absent: merges in Merge with the home's, confirmed by f7-merge
    pr: {number: 7, ci: green, head: 9f8e7d6}  # absent when its branch adds nothing to its trunk
    merged: 4c3b2a1              # the merge the loop confirmed
steps:
  - id: f1-design                # <f|x><phase>-<name>[-r<n>]
    phase: 1
    affinity: cloud              # cloud | human | host:<name> (FLOW-04)
    repo: buildwarden/buildwarden-specs  # optional, host steps: the work entry it runs in; absent: the home
    status: pending              # pending | done
    needs: [f1-answer-q1]        # step ids that must be done first
    lease: {claimed_by: "cloud/20261029T095500Z", expires: 2026-10-29T11:55:00Z}
    note: optional
budget:                          # FLOW-13 runaway check on open items only, in steps; not a share of the run
  estimate: {runs: 4, steps: 18}
  spent: {runs: 1, steps: 3}     # a claim counts a step, except a refresh's first claim, which counts in
                                 #   the run's budget and not the item's (FLOW-13); a run's first claim counts a run
questions:                       # FLOW-07; never GitHub issues
  - id: q1
    kind: blocking               # blocking | assumed
    status: open                 # open | answered (blocking) | confirmed (assumed)
    question: ...
    options: [...]
    recommended: ...
    answer: set by the human
history:                         # append-only
  - {at: 2026-10-29T09:55:00Z, by: cloud/20261029T095500Z, event: claimed f1-design}
```

Every field from `repos` to `collides_with` is optional, and a file without
them behaves as before. `wf declare -state DIR -repo DIR -worker W -feature F`
writes `repos`, `areas`, `seams`, `rules_changed`, `alters_relationships`,
`design_review` and `declared` from the design on the item's branch: any value
before Design is done; nothing in Plan; from Implement on, an agent may only
add areas within the approved design; a `human` worker may write any value
after Design. `wf new` takes `-repos`, `-areas`, `-seams`, `-adopts` and
`-urgent`, and with `-follows` and no `-areas` copies that item's `repos` and
`areas`. `wf relate -worker human/<name> -feature A -with B [-clear]` writes
`collides_with`. `wf status` prints `repos:`, `areas:`, `declared:`, `adopts:`
and `urgent:` lines under an item that has them.

### Steps and phases

Each phase starts with template steps, and the phase's last template step is
its **gate**: marking it done runs the phase's FLOW-03 done-when check, and
the transition happens only if the check passes.

| Phase | Steps |
|---|---|
| 0 | `f0-branch-setup` |
| 1 | `f1-design` (decides `design_review`) |
| 2 | `f2-plan`, then `f2-design-review` (human, FLOW-19) unless `design_review: skip` |
| 3 | `f3-implement` |
| 4 | `f4-review` |
| 5 | `f5-guide` |
| 6 | `f6-merge-main` (waits for the PR slot, FLOW-05), `f6-consolidate`, `f6-open-pr` (archives the design on the branch and opens the PR; no confirmation, FLOW-08); `f6-refresh` (below) |
| 7 | `f7-merge` (cloud; passes once the human has merged, takes no claim or budget; never offered by `wf next`, the tick confirms it) |
| 8 | `f8-close` (cloud, inline in the tick; no PR, FLOW-16) |

A **process item** (`kind: process`, FLOW-03) changes the rules the loops run
under (`docs/development/`, `.claude/`, `tools/workflow/`). It has its own
round, `process`: `x1-design` (human: the design on the branch, approved in its
design review), `x2-implement` (cloud: implemented, archived and its PR green),
`x3-merge` (merged into `main`) and `x4-close` (branch gone, design archived on
`main`).

A **tracked** item (round `tracked`, step letter `t`) is homed in another
repository, where `wf` sees no branch, design or PR: `wf new -repos
<owner>/<other> ...` seeds `t1-work` (human: the design, the work and the
review, until its PR is open) and `t2-merge` (human: Jeff merged it). `wf done`
runs no check for either; any claim starts it; it neither holds nor waits for
a limit, and its `seams` are what intake records with `wf new -seams`. An item
homed here that also works in a second repository is not tracked: it lists
both in `repos`.

The **refresh**, `f6-refresh` (`x2-refresh` on a process item; `-r2`, ... as
needed), is a `cloud` step that no phase seeds. `wf stale -state DIR -repo DIR
-worker W` names an item whose PR the human has merged and seeds no refresh for
it (the merge step is the cloud's: the tick's merge confirmation completes it,
and an attended session cannot), then seeds one on each item waiting for the
human's merge whose branch does not contain `origin/main`, or whose head is not
`pr.head`, and sets `pr.ci` to `pending`. It merges `main`, runs the gates and
the consolidation pass, pushes, and records `pr.ci` and `pr.head` for the new
head (FLOW-10). A PR is ready to merge only while its branch contains `main`
with its checks green on that head (FLOW-08). No refresh is taken while
`main.yaml` records `main` red, except the fix it names.

`wf next` orders open items by class (FLOW-05): in implementation, then process
items, then fixes (`follows`), then new functionality; within a class in
progress before queued, then priority. While a process item is in progress, `wf next`
gives a worker matching its `holds` (`cloud`, `host:*`, `host:macos-vz`) no
new step and reports `held by process item <name>`; `wf claim` refuses it and
`wf gate` starts no sweep for a held host. A step already claimed stays
claimed, and finishing the process item releases the hold. Intake:
`wf new ... -kind process -holds cloud,host:*`.

`wf new ... -hold "<why>"` files an item on hold (FLOW-20's freeze, FLOW-07): it
writes a blocking question `q1` whose text is the reason, and a human step
(`f0-answer-q1`, or `x1-answer-q1` for a process item) that the item's first
step needs. `wf answer -question q1` releases it. Quote the reason: `wf` stops
reading flags at the first bare word, so an unquoted reason, or an unquoted
multi-word value before `-hold`, drops the hold without an error; check the
file `wf new` wrote before committing.

Design adds the steps it finds: `f1-answer-<q>` (human) for a blocking
question, `f6-validate-<host>` (`host:<host>`) for blocking native validation.
A return to Design (`wf back`, FLOW-06) re-seeds phase 1 with `-r<n>` ids, so
Plan seeds a fresh design review; the third return adds a human `escalate`
step. Consolidation returning work the approved plan covers uses
`wf back -to 3` (back to Implement, no new review). Items finished before
workflow-streamline keep their `p`/`m` step ids as history; `wf migrate` moved
the unfinished ones on 2026-10-31.

`wf declare` keeps an entry's `pr` and `merged`, and refuses to drop an entry
whose branch is on its remote. `wf validate` checks that `work` and `repos`
agree once declared; an item declared before `loop-repository` has no `work`
and behaves as before until it is declared again. A bare area name is the
home's; `<owner>/<name>:<area>` names another repository's.

## `hosts.yaml`

```yaml
machines:
  - name: windows-desktop
    hosts: [windows-hyperv, container-any, linux-kvm]
    repositories: [buildwarden/buildwarden]   # optional; absent: config.yaml's repository only
```

`wf gate` and `wf next` offer a host step only to a machine that serves its
host name and lists the step's repository (its `repo`, else the item's home),
and a led item's steps only to a machine that serves the lead and lists every
repository in the item's `repos`. `wf validate` fails a host step or a lead
that no serving machine can take, naming the machines, the host name and the
repositories to add; `wf lead -host`, `wf new -lead` and `wf declare` refuse
to create one. `native-tick.sh` resets each listed repository's clone
(`wf native -clones`) to its trunk at the start and end of each run.

## Claiming a step

Workers are `cloud`, `human` or `host:<name>`, with a `/<session>` suffix that
tells their leases apart. From a checkout of `main`, with this branch checked
out at `.dev/workflow`:

```bash
(cd tools/workflow && go build -o ../../dist/wf ./cmd/wf)
dist/wf next   -state .dev/workflow -worker cloud/$RUN
dist/wf claim  -state .dev/workflow -worker cloud/$RUN -feature F -step S
dist/wf commit -state .dev/workflow -worker cloud/$RUN -m "F: claim S" -claimed F/S queue/F.yaml
# wf claim works out whether the claim starts a new run from the worker and the
# item's history; -new-run is accepted and ignored (loop-streamline-2)
# ... do the step ...
dist/wf done   -state .dev/workflow -repo . -worker cloud/$RUN -feature F -step S -run
dist/wf commit -state .dev/workflow -worker cloud/$RUN -m "F: done S" queue/F.yaml
```

`wf commit` replaces `git commit` and `git push`: it regenerates `QUEUE.md` and
the digest pages, stages only the paths given and those, commits and pushes.
On a rejected push it fetches and resets to `origin/workflow`: without
`-claimed` it replays the change; with `-claimed` it asks the claim again on
the new state and exits 4 if it is refused (FLOW-04): ask `wf next` again.
Exit 5: the change could not be replayed, or the push was rejected on every
try; it names the files. It refuses a change to `areas.yaml` from a worker that
is not `human/<name>`. An expired lease may be reclaimed. State is written after every step, so an
interrupted run loses at most the step in progress (FLOW-13).

`wf next` follows FLOW-05: the first ready step in class order (in
implementation, which an item with a pending refresh is; process, fixes, new
functionality; in progress before queued, then priority); a fix only once the item it `follows`
is done, unless an attended run names it. It skips an item waiting on the
human's merge (its `f7-merge` or `x3-merge`). Its `blocked` lines feed the
digest.

**The guard.** One check (`Guard`), applied by `wf next` and `wf claim` for
every worker, decides the limits. Two items are *colliding* (they share an
exclusive area or a seam with no specification, they share a repository
that has no map or one of them is undeclared, or the human said so with
`wf relate`), *near* (both change a seam that has a
specification, or the same rule, or an area of one reaches an area of the
other) or *disjoint*; `wf relations
[-feature F]` prints each pair that is not disjoint, with the reason. A
process item is outside the relations and every limit; a tracked item is in
the relations and outside the limits. Each limit counts an item with the
holders that relate to it, and no holder's set may number more than the
limit:

| Limit | Taken by | Held while | Counted with | At most |
|---|---|---|---|---|
| In progress | the claim that starts a queued feature | the feature is in progress | the in-progress features that collide with it | `limits.in_progress` |
| `alters_relationships` slot | the claim of a Plan step, by a feature that declares `true` | a Plan step is done or carries a claim, expired or not; `wf release` on an unfinished Plan step gives it back | the holders that collide with it | `limits.alters_relationships` |
| PR slot | the claim of `f6-merge-main` | in Publish with its newest `f6-merge-main` done or claimed, or a PR recorded and not yet in Close | the holders that collide with it or are near it | 1 |

**The waiting limit** counts no relation: no queued feature starts while
`limits.waiting_on_human` or more items in progress wait on the human (a due
`human` step, an open blocking question, a PR at its merge step, a spent
budget), each counted once. It never refuses a step of an item in progress, a
process item, a tracked item, a fix (`follows`), the fix `main.yaml` names for
a red `main`, or a feature marked `urgent`. The cloud also skips a feature with
an open blocking question or a spent runaway budget, and a refresh while
`main` is recorded red.

**Leads.** A led feature's template steps of Branch setup through Guide that
would be `cloud` carry its lead's `host:<name>` instead; its design review
stays `human`, and Publish, Merge and Close stay `cloud`. A claim by a worker
that serves the lead starts a queued led feature, and no other claim does.
`wf lead -worker W -feature F -host <name> | -clear` (any worker) relabels
each pending step of phases 0-5 whose lease is not held, and writes one
history line naming the old and new lead and the steps changed and left; a
held step keeps its affinity until done or released. `wf new -lead
host:<name>` sets it at intake. A lead changes no position or limit. On a
machine, a led step runs in a worktree `.scratch/<item>`, never in the
wrapper's checkout, and its branch is pushed only by
`tools/workflow/native/native-push.sh <name>`.

**Leases.**

| Worker | Lease on claim | Renewed by | Released early by |
|---|---|---|---|
| `cloud/<run>` | `lease_minutes` | claiming again | `wf release`, by the run |
| `human/<name>` | `lease_minutes` | claiming again | `wf release` |
| `host:<name>/<machine>.<run>` | `host_lease_minutes` | `wf renew`, by the session | the session (`wf release`); the wrapper when the session ends (`wf release -session <machine>.<run>`); the machine's next wrapper run (`wf release -machine <machine> -stale -current <machine>.<run>`) |
| `host:<name>/<machine>.attended-<UTC>` | `host_lease_minutes` | `wf renew`, by the session | the skill's Close (`wf release -session <machine>.attended-<UTC>`); otherwise the expiry |

`wf renew -worker W -feature F -step S` refuses unless the step is pending
and its live lease is W's; it sets a new expiry, logs "renewed S until T" and
spends no budget. `wf commit -renewed F/S` pushes it, and on a rejected push
asks the renewal again on the new state, exiting 4 if refused (then the
session stops working on the step). `-stale` never releases the current
run's session or an attended one.

Other commands: `wf validate [-areas <candidate> [-repo DIR]]` (with `-areas`,
what a candidate map does to the open items), `wf status [-all]` (open items;
`-all` adds done ones), `wf check` (done-when without moving), `wf release`,
`wf back` (FLOW-06), `wf answer` (human only, FLOW-07), `wf new` (intake),
`wf urgent`, `wf relate` and `wf move` (human only), `wf lead`, `wf renew`, `wf release -session | -machine -stale`, `wf migrate -done` (once, at queue-positions' `x4-state`; refused once `queue/done/` exists), `wf declare`, `wf relations`,
`wf stale`, `wf main` (records `main`'s CI and its up-to-date setting in
`main.yaml`), `wf areas -list | -check [-rev REV] [-edges FILE|-]` (a report,
never a gate), `wf digest`, `wf commit`, `wf budget [-native]`.
