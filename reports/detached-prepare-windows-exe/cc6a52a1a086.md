## Findings

### F1: GLOBAL-06, MUST-review: `driver/detach.go:53`

This change moves the `host-env` boundary. It changes which executable
warden runs on the host to make the prepared base or layer, which every
later build environment boots. Before, on Windows, `os/exec`'s `PATHEXT`
lookup ran `<exe>.exe` (or another extension) from beside an extension-less
`dist/warden`. Now `os.StartProcess` runs exactly the file that
`os.Executable()` names. The design carries the Security note this rule
requires: the posture before and after, the SEC-01 cell and the TEST-08
case. That note was reviewed at r1 and r2. `TestStartDetachedRunsNamedFile`
tests the case at the unit level. Case 3 of the blocking `windows-hyperv`
step tests it natively.

**Fix:** no code change. The human acknowledges F1 at merge, with the Security
note in the PR body. The blocking `f6-validate-windows-hyperv` step (cases 1
and 3) supplies the evidence on Windows, the only OS where the fault exists.

## Judged and not findings

- **The design as written.**
  - `StartDetached` calls `os.StartProcess(exe, [exe]+args)` with `{null, log, log}`, `os.Environ()` and `detachedAttr()`, then releases the process.
  - On a failed start, it writes `[warden] could not start <exe>: <err>` to the open log and returns the error.
  - `os/exec` is gone from `detach.go`. `detachedArgs`, `detachedAttr`, `ConfigFile` and `TestDetachedArgs` are unchanged.
  - When the start fails, both callers print the Note C line and return nil. The qemu caller also prints it on a `TryHostLock` error, and a held lock stays silent.
  - The success lines are unchanged. qemu takes `progress`, and `resolveWindowsBaseImage` passes `os.Stderr` (Note B). The test seams are unexported package variables (Note A).
- **GLOBAL-09, -10 and -11.** No default, merge or fallback appears that the **Defaults and overrides** section does not list.
  - The null stdin and inherited environment are what `exec.Cmd` did with nil `Stdin` and `Env`, and Decision 1 names both.
  - "The build goes on" is named there and is not a fallback: nothing runs in place of the start.
  - The `PATHEXT` lookup was an unnamed fallback, and the diff removes it.
- **UX-04.** Each new line names what failed, the error, and the exact command to run by hand. The command comes from `prepareFix` or `prepareFix(ga)`, so it is spelled in one place. The build goes on, so the line is a warning and no `FixableError` is needed.
- **Hyperv lock errors.** `prepareRunning` is unchanged. It treats a lock error as "not running" and starts the prepare, so hyperv never dropped a lock error silently. The design's qemu-only handling is right.
- **Task 7.** No other place re-executes warden through `os/exec`.
  - The non-test `os.Executable()` sites look up files beside the executable, run `codesign -d` on it (vz), register it with the SCM (hyperv), or prepend its directory to PATH (warden-io).
  - No code calls `exec.Command(exe …)`.
  - The PR body should list this.
- **TEST-04.** The tests are deterministic.
  - The detached-start test polls the child's log line until a 30s deadline and fails there, with no retry.
  - The freshness tests use a 2h age against a 1m refresh age.
  - On Windows, the released child may still be exiting when the cleanup deletes the copied `warden`. `testing.removeAll` retries for 2s, which covers that. It is worth watching in native case 1.
- **ORCH-04.** No transient resource is added. The null handle and the log are closed by `defer`.
- **ORCH-01 and TEST-02.** All five drivers are declared (a5). The container, vz and firecracker trees are not edited, and none of them calls `StartDetached`.
