## The stale-service fix (ff17b4e, ae9f8e0, 2dc2cfa)

- **GLOBAL-11: is a stale service ever treated as absent?** No: a stale service is never treated as absent. probeService returns absent only when the pipe does not open; once it opens, every failed ping (another protocol version, no version, a decode failure or the 2 s deadline) is stale with its reason, and ServiceReachable and ServiceStale are exclusive. A non-elevated process with a stale service gets NetBlocked (capability.go:181) before the durable case, Ready refuses it first (203), and doctor prints 'stale: it <reason>' with the fix, never 'not installed' or 'has no build switches'. Elevated ignores it (serviceBlocks, 223), the only path that never uses the service. No new default, merge or fallback: the strategy order loses the durable fallback for this case, which is the GLOBAL-11 direction.
- **UX-04: is the reinstall fix right?** Right. serviceReinstallFix (service.go:40) names 'from an elevated shell, run `warden hyperv service uninstall`, then `warden hyperv service install`', matching InstallService's refusal while the service is registered (service_windows.go:156-161) and the cobra commands (cmd/warden/host.go). buildRefusal returns a driver.Fixable with that fix and the reason as its message; doctor prints it under the service line and the Network line; the new service's own mismatch reply names it too (service.go:77-81). pingService does not surface the protocol-1 service's own 'install'-only text.
- **TEST-06: do the tests fail if the stale path regresses?** Mostly: see S7 for the windows-only link. The protocol1Service fake matches main's version-1 handleServiceRequest (Version 1 in the reply, Err set before the op is read).
- **The design's Compatibility edit against task 28** Consistent with task 28, no new decision. Task 28 and the plan note bump serviceProtocolVersion 1 to 2 and ask for 'a refusal both ways' (Decisions 9, 11); the new row records that refusal and that an old service is never read as absent (GLOBAL-11), and the edit to the older-setup row drops 'service builds unaffected', which the bump made untrue. Decisions and Defaults and overrides are unchanged. See the informational note on the plan note's wording.

## Findings

### M1. GLOBAL-10 (MUST): `tools/relay-vm/init:164-172` (fixed)

Caused by: diff.

**Fixed in e53b12e**: on Hyper-V the init no longer reads /proc/cmdline's keys (read_keys over it runs only in the else branch), and a warden.* word on the Hyper-V command line stops the init before the seed is read, naming the key ('stopped: warden.<key> on the kernel command line: on Hyper-V the relay seed (WARDENRELAY) alone carries the boot keys'). TestRelayInitHyperVSeedAlone pins the branch shape and the refusal's order; README and overview.md pseudocode updated (FLOW-15). The refusal is not a default or merge, so nothing new to list in Defaults and overrides.

Was: On Hyper-V the init runs read_keys over /proc/cmdline and then over the relay seed into the same variables, so a seed key silently overrides the same command-line key and a command-line key the seed omits is kept: a per-key merge of two boot channels. The design's Defaults and overrides says 'the seed and the command line never both supply a key (Hyper-V reads the seed's values)' and names no merge. Today it has no effect (the UKI command line is 'console=ttyS0 console=tty0' and warden's seed writes every key), but the code lets a seed with no claim_token run with one from the command line.
