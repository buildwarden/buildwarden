## Findings

### M1. GLOBAL-10 (MUST): `tools/relay-vm/init:164-172` (fixed)

Caused by: diff.

**Fixed** in e53b12e: on Hyper-V the init no longer reads /proc/cmdline's keys (read_keys over it runs only in the else branch), and a warden.* word on the Hyper-V command line stops the init before the seed is read, naming the key ('stopped: warden.<key> on the kernel command line: on Hyper-V the relay seed (WARDENRELAY) alone carries the boot keys'). TestRelayInitHyperVSeedAlone pins the branch shape and the refusal's order; README and overview.md pseudocode updated (FLOW-15). The refusal is not a default or merge, so nothing new to list in Defaults and overrides.

Was: On Hyper-V the init runs read_keys over /proc/cmdline and then over the relay seed into the same variables, so a seed key silently overrides the same command-line key and a command-line key the seed omits is kept: a per-key merge of two boot channels. The design's Defaults and overrides says 'the seed and the command line never both supply a key (Hyper-V reads the seed's values)' and names no merge. Today it has no effect (the UKI command line is 'console=ttyS0 console=tty0' and warden's seed writes every key), but the code lets a seed with no claim_token run with one from the command line.

### M2. UX-04 (MUST): `driver/hyperv/setup.go:110-117; driver/hyperv/ensurenet.go:47-55; driver/hyperv/provision_local_windows.go:91-99` (fixed)

Caused by: diff.

**Fixed** in aff6ffd: RunSetup goes through ensureSetupNAT, which refuses (driver.Fixable) a NAT whose name is not <network>-nat that owns the prefix, naming it, the NAT durable builds use, and the fix (remove it once nothing uses it, or pass another --nat-prefix). EnsureNetwork only adopts in that case, so the refusal comes before setup changes anything. TestSetupRefusesNATDurableBuildsReject pins the three cases with a fake Provisioner; cli.md and overview.md updated (UX-01, FLOW-15).

Was: Setup passes no DevNAT, so EnsureNetwork takes any NAT that owns the --nat-prefix, whatever its name (another build's per-build NAT, or a non-warden NAT). Setup then prints 'Durable dev network ready' naming it. VerifyNetwork reads only <network>-nat (netProbeScript with no otherPrefix), so every durable build is refused with 'the durable network's NAT "warden-dev-nat" is missing', and its fix ('run warden setup') succeeds again without changing anything. The user loops. On main, VerifyNetwork checked only the Private switch. Decision 5 says the durable strategy uses <switch>-nat. (Pre-review candidate 7, confirmed.)

### S2. GLOBAL-09 (SHOULD): `driver/hyperv/setup.go:169-175 (ensureSetupNAT)` (open)

Caused by: diff.

Open, carried over from 525e36a6c04c. The prefix-mismatch refusal moved into ensureSetupNAT unchanged: it still compares against opts.NATPrefix after applyDefaults, so it fires when --nat-prefix was never passed. Re-running 'warden setup --driver hyperv --slots 8' on a host set up with --nat-prefix 10.200.0.0/24 is refused 'not --nat-prefix 192.168.240.0/20', naming a flag the user did not pass and telling them to delete their NAT. The design does not name this refusal, and Decision 5 has builds use the dev NAT 'whatever prefix setup gave it'. --host-ip is still not compared, so an explicit --host-ip that differs from an existing NAT's is silently not used. The new M2 refusal has the same wording shape ('already owns --nat-prefix <default>') but is correct either way, since another NAT on the prefix does break durable builds.

**Fix:** Compare only flags the user gave: refuse an explicit --nat-prefix or --host-ip that differs from the existing <network>-nat, and without them adopt the existing NAT and print what was read back.
