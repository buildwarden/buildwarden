## Findings

### M1. GLOBAL-10 (MUST): `tools/relay-vm/init:164-172`

Caused by: diff.

On Hyper-V the init runs read_keys over /proc/cmdline and then over the relay seed into the same variables, so a seed key silently overrides the same command-line key and a command-line key the seed omits is kept: a per-key merge of two boot channels. The design's Defaults and overrides says 'the seed and the command line never both supply a key (Hyper-V reads the seed's values)' and names no merge. Today it has no effect (the UKI command line is 'console=ttyS0 console=tty0' and warden's seed writes every key), but the code lets a seed with no claim_token run with one from the command line.

**Fix:** On Hyper-V take the keys from the seed only: stop with a console line when /proc/cmdline carries a warden.* key (naming it), or skip the command-line read_keys when HYPERV=1. Add a driver/relayvm/init_test.go case.

### M2. UX-04 (MUST): `driver/hyperv/setup.go:110-117; driver/hyperv/ensurenet.go:47-55; driver/hyperv/provision_local_windows.go:91-99`

Caused by: diff.

Setup passes no DevNAT, so EnsureNetwork takes any NAT that owns the --nat-prefix, whatever its name (another build's per-build NAT, or a non-warden NAT). Setup then prints 'Durable dev network ready' naming it. VerifyNetwork reads only <network>-nat (netProbeScript with no otherPrefix), so every durable build is refused with 'the durable network's NAT "warden-dev-nat" is missing', and its fix ('run warden setup') succeeds again without changing anything. The user loops. On main, VerifyNetwork checked only the Private switch. Decision 5 says the durable strategy uses <switch>-nat. (Pre-review candidate 7, confirmed.)

**Fix:** In RunSetup, refuse (driver.Fixable) when res.NATName is not <network>-nat, naming the NAT that owns the prefix and how to remove it or choose another --nat-prefix, so that setup succeeds only on a NAT durable builds accept. Pin it with a pure test of the setup decision.

### M3. GLOBAL-04 (MUST): `relay/relay.go:188-200`

Caused by: diff.

New behavior: when CollectorTransport is nil, a direct CollectorURL that names a host dials through the relay's resolver list (a cloned default transport with upstreamDialContext). No test covers it: every relay test sets CollectorTransport or uses an IP or placeholder URL. warden's drivers use the tunnel, so only third-party claimants reach this path, but it is the relay's only output path (RELAY-07). (Pre-review candidate 8b, confirmed.)

**Fix:** Add a relay test: CollectorURL http://collector.example:<port> with no CollectorTransport, a fake resolver from upstream_dns_test.go that answers 127.0.0.1, and a check that the collector receives the sink's request and the resolver was asked.

### S1. GLOBAL-09 (SHOULD): `tools/relay-vm/init:28,158`

Caused by: diff.

The init keeps warden.net=dhcp as its default when the key is absent. The diff changes Hyper-V's default from static to dhcp, and the design's Defaults and overrides does not list the default. Every warden driver now sends warden.net (qemu vm.go:35 dhcp; firecracker vm.go:62 static; the Hyper-V seed static), so no driver reaches the default. (Pre-review candidate 2, confirmed.)

**Fix:** Require warden.net: stop naming it when absent, as warden.seed is required (this removes a default, in keeping with Decision 2). Or go back-to-design (FLOW-06) to list it.

### S2. GLOBAL-09 (SHOULD): `driver/hyperv/setup.go:118-124`

Caused by: diff.

The new prefix-mismatch refusal compares against opts.NATPrefix after applyDefaults, so it fires when --nat-prefix was never passed. Re-running 'warden setup --driver hyperv --slots 8' on a host set up with --nat-prefix 10.200.0.0/24 is refused 'not --nat-prefix 192.168.240.0/20', which names a flag the user did not pass and tells them to delete their NAT. The design does not name this refusal, and Decision 5 has builds use the dev NAT 'whatever prefix setup gave it'. --host-ip is not compared at all, so an explicit --host-ip that differs from an existing NAT's is silently not used (main ignored it too, and printed it as if applied). (Pre-review candidate 6, confirmed.)

**Fix:** Compare only flags the user gave: refuse an explicit --nat-prefix or --host-ip that differs from the existing <network>-nat, and without them adopt the existing NAT and print what was read back.

### S3. GLOBAL-01 (SHOULD): `tools/relay-vm/hyperv/build.sh:181`

Caused by: pre-existing line; misdescribes this diff's channel.

The build's last echo still says 'Per-build kernel cmdline (relay config) is layered by the driver, not baked here.' Hyper-V has no per-build command line: the relay seed carries the pre-claim values, and the claim carries the configuration (RELAY-08). The line was already wrong on main, but the diff edits this file and adds the channel the line misdescribes. (Pre-review candidate 4, confirmed.)

**Fix:** Change it to say the relay's pre-claim values come per build on the relay seed (WARDENRELAY) and everything else in the claim. One line, in a file the branch already edits, so no follow-up was filed.

### S4. TEST-06 (SHOULD): `relay/upstream_dns_test.go:195-246; relay/proxy.go:98-150`

Caused by: diff.

The 71df1d1 fold-in (the relay's own lookups go through the DNS handler's in-order forwarder, not a net.Resolver whose retries restart at the first server) is only partly pinned. TestUpstreamDialResolvesThroughList asserts that both servers were asked and UPSTREAM_DNS was not. A net.Resolver with a list-walking Dial would pass it too. (Pre-review candidate 8a, confirmed as a gap.)

**Fix:** Pin the property: per query, the silent first server is asked once and then the second, with one 'did not answer' log line per timed-out server, and no restart at the first server within a lookup.

### S5. TEST-06 (SHOULD): `cmd/relay/main.go:141-180; cmd/relay/upstream_test.go:86-120`

Caused by: diff.

serveClaim's new wiring has no test: the refusal path's done() cleanup of the mode step, container mode's DetectSelfIP, and cfg.UpstreamDNS/UpstreamDNSSource set from upstreamResolvers. TestAbsentUpstreamDNSRefusalLeavesRelayClaimable copies the callback rather than driving serveClaim, so 'a refused claim leaves the relay claimable' is not tested in the vm-mode and host-mode wiring, where the step builds the netstack or addresses the link. (Pre-review candidate 8c, confirmed.)

**Fix:** Factor the claim callback out of serveClaim (it takes the step and readConf) and drive it with a fake step that records its cleanup: a refused claim runs done() and a second claim succeeds.

### S6. TEST-06 (SHOULD): `driver/qemu/driver.go:80; driver/vz/driver.go:464`

Caused by: diff.

setRelayDNS is table-tested in both drivers, but nothing fails if Build stops calling it. The claim would then carry the raw [vm] dns or no upstream_dns, and the relay would fall back to its own resolv.conf. The f6 qemu-any and macos-vz steps would catch this natively. (Pre-review candidate 8d, confirmed.)

**Fix:** Assert that a qemu and a vz build request reach the claim with upstream_dns set, for example through the session's claim fake, or accept native validation as the cover and dismiss.
