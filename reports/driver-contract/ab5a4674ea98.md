## Findings

### 4. FLOW-06 (MUST): `warden shell` builds start no waiter, so the scan never keeps them

**Status:** new in r4.

**Where:** `driver/container/container.go:110` and `:131` (`runHeld`). Also `docs/book/src/guide/cli.md:408` and the design's Behaviour 6 (`driver-contract.md:4363-4370`). Related: ORCH-04, DRV-27, UX-01.

Decision 25 says that `run` starts the waiter by the container's name, and that the scan counts a build only by that waiter under a live driver. Behaviour 6 says that a running build of another user on docker or finch "is now kept" and that "what it removes is what is not running".

The code starts the waiter only in `mode: build`. `watchExit` and `containerWait` are called at `container.go:117`. `mode: shell` returns into `runHeld` at `:110`, and `runHeld` never starts a `container wait`. `attach`'s `<rt> container exec -i -t warden-build-<id> ...` is not a waiter either.

So another user's live `warden shell` session (another `HOME`, so its lock is not in `keep_ids`) has nothing the scan counts. This user's `warden clean` tears it down on every runtime. This is the same failure as finch case 6, the case r4 exists to fix, for the shell.

- On podman, `main` kept such a session through `conmon -n warden-build-<id>`. r4 drops that sign, so this is a regression on podman.
- On docker and finch, `main` did not keep the session either: its shell exec named the 64-hex ID.
- `guide/cli.md:408` now promises that "a running build is left alone while its `warden-driver-container` runs, even another user's". For a shell this is not true.

The design does not name the gap. Its `run` row and Decision 25 cover `run` in both modes.

**Fix:** in `runHeld`, once the held build container runs, start the same waiter by name, under the driver: `waitArgs`, through `watchExit` or a bare `containerWait` whose result `runHeld` handles. Add a test that a held `run` starts it. If Implement finds that a waiter cannot fit `mode: shell` (for example, what its `exited` should mean during a shell), the work goes `back-to-design` (FLOW-06) instead, to name the gap. Either way, keep `cli.md:408` true to the result.

## Implement's recorded deviations, judged

1. **The refusal prints twice.** Judged: not a finding.
   - First comes the driver's relayed stderr line, `[warden] driver container: --runtime names the container runtime podman, which is not installed (not found on PATH)`. Then warden's `[warden] ERROR:` with its `To fix:`. This was reproduced with `warden build --runtime podman`, `WARDEN_CTR_CLI=podman`, `[driver.container] cli` and `warden doctor`.
   - The kit writes every error's message to the driver's stderr (`driver/drivercmd/main.go:122` and `:281`, since task 13), as its log (DRV-40). warden relays that log, then prints the error object.
   - So every probe refusal on the branch prints twice. An example is the r3-era `--runtime nope`, which prints `--runtime is "nope"; ...` twice. r4 adds nothing new here, and the guide's examples show only warden's lines, as the existing example at `configuration.md:494` does.
   - Collapsing the two is a kit-wide and warden-wide change, not this rework's. See Informational.
2. **The ps parse splits at blanks.** Judged: partly moot, and the rest is informational.
   - **The runtime half cannot happen.** The driver starts the waiter as `exec.Command(<bare name>, ...)`, and the runtime setting is limited to a bare `finch`, `docker` or `podman` (paths are refused: `runtime_former.go`). So the waiter's `argv[0]`, which `ps` prints, is never a path.
   - **The driver half is real.** warden runs the driver as `exec.Command(<full path>, "run")` (`cmd/warden/drivercall.go:633`, `:769`). A driver whose path holds a space has `path.Base(parent.args[0])` of the path's first word (`clean.go:204`), not `warden-driver-container`. Another user's running build under such a driver is then removed, which is the direction Decision 25 exists to prevent. Its own user's builds are still kept by `keep_ids`.
   - The design's wording is "the base name of its first argument", and that argument's base name is right, so the code meets the design only for paths without blanks. The design accepts the same kind of degradation to `keep_ids` for BusyBox `ps` ("What Decision 25 relies on", `driver-contract.md:5219`), but does not name this one.
   - A fix inside the design is small: read each line as PID, PPID and the rest of the line, and take the parent as the driver when that rest, less a trailing ` run`, has the base name `warden-driver-container`.
   - Not counted: see Informational for the choice.
3. **The fake counts `waiter.pid`'s presence as a live child, with no check that the process lives.** Judged: not a finding.
   - The fault plays a broken driver, one that takes a process naming the build for a sign of life.
   - In the Clean case, the waiter really is alive when `clean` runs. It sleeps for an hour and is killed only by `stopRelay`, through teardown, reap or `clean`. A check with signal 0 would give the same answer.
   - The self-test sees the Clean case fail under the fault, and `stopStubRelays` now also kills waiters (`*.pid`), so nothing outlives the test.
