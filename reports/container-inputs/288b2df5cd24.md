## Findings

### ORCH-02 (MUST): `driver/qemu/driver.go:147`, also `driver/hyperv/driver_windows.go:125`

**What is wrong.** qemu and hyperv call `RecordInputs` only on the success path, after `sess.Wait` or `runBuild` returns nil. A failed Linux-guest build from a Dockerfile gets no `inputs/`, and that is exactly when a user wants to compare what ran with what they wrote. The container driver records from `teardown()`, so its failed builds do keep `inputs/`. ORCH-02 has no success condition. `docs/book/src/guide/output.md:32` also says qemu and hyperv write `inputs/` for any Linux guest built from a Dockerfile.

**Suggested fix.** Record inputs on every path once the script is staged. The simplest way is to call `RecordInputs` right after `StageBuildScript`: the output dir already exists and both files are final at that point. A defer after staging also works.

### ORCH-01 (MUST): `driver/hyperv/driver_windows.go:125`, also `driver/qemu/driver.go:147` and `driver/container/container.go:840`

**What is wrong.** Each driver handles the same `RecordInputs` failure differently, and the design does not say why:

- **Container:** logs a WARNING, and the build reports SUCCEEDED.
- **qemu and hyperv:** return an error after the build and ledger have completed. `cmd/warden` `runBuild` passes that error to `buildFailed`, the `BuildResult` is dropped, and a successful build is reported as FAILED.

ORCH-01 allows a per-driver divergence only where the platform differs and the design states the reason. Nothing platform-specific is involved here.

**Suggested fix.** Pick one policy and record it in the design's Decisions. The two options are fail (ORCH-02 is a MUST) or warn. Apply the same policy in all three drivers. If inputs are recorded at staging time (see the ORCH-02 finding above), a recording failure fails before any VM or container starts (UX-04, check early), and the post-build divergence goes away.

### ORCH-02 (MUST): `driver/session.go:384`

**What is wrong.** `RecordInputs` re-reads `req.Containerfile` from the user's tree at the end of the build, not when it was translated:

- `inputs/build.sh` is the staged copy, which is what actually ran.
- `inputs/Dockerfile` is whatever the file holds minutes or hours later.

An editor save or `git checkout` during the build would pair a Dockerfile with a translation it did not produce. `output.md` documents that file as "Your Dockerfile, unchanged". The old container-only code had the same timing; this diff moves it into the shared helper and extends it to qemu and hyperv. Likelihood is low, but the file is a provenance record.

**Suggested fix.** Capture the submitted bytes when `StageBuildScript` translates them, either by copying into `workDir` next to the script or by writing to `<output>/inputs/` at staging time. Then copy that capture, not the live path. This fits with the staging-time fix for the first finding.
