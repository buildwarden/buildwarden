### MUST-review

2. **GLOBAL-06** (ORCH-04, UX-04), `driver/firecracker/slots.go:138`.
   - **What's wrong:** re-running `warden setup` drops the isolation of slots that are in use.
     - `setupSteps` starts with `flushSteps`: these delete every WARDEN-FC jump, both chains and the `warden_fc` bridge table. The jumps come back only at the very end.
     - Each slot also runs `ip addr flush dev wfc<i>u` and re-adds the address (line 209).
     - For the whole run (about 40 execs per slot), a slot with a running build has no isolation rules:
       - any local user can reach the relay's unauthenticated `:8300` control plane (the a10 filter is gone);
       - INPUT from `wfc<i>u` is open, so a compromised relay can reach host services;
       - only the sysctl layers stand between the build VM and the host;
       - the address flush also breaks the running builds' claim tunnels.
   - **Why it matters:** re-running setup is expected. The docs call it idempotent, a8's native host and the CI job re-run it each time, and growing `--slots` on a busy fleet host means re-running it.
   - **Suggested fix:**
     - Reload atomically: use `iptables-restore --noflush` and `ip6tables-restore`, or build new chains and swap the jumps. Load the bridge table in one `nft -f` transaction.
     - Skip the address flush when `host(i)/30` is already present.
     - Alternatively, refuse setup while any slot has live VMMs.
     - Add a tier-0 test that the step list never leaves the hooks without a WARDEN-FC jump.

### SHOULD

3. **UX-04** (ORCH-04), `driver/firecracker/doctor.go:340`.
   - **What's wrong:** under sudo, the orphan, reflink and KVM rows check root, not the user builds run as. Only `slotUID` follows `SUDO_USER`; `LockDir()` and `WorkRoot()` both follow `os.UserCacheDir()`.
     - **Default sudo** (HOME is `/root`): the orphan check reads root's empty lock dir and prints `ok` falsely, the reflink check probes the wrong filesystem, and `/dev/kvm` always opens.
     - **`sudo -E`, or a sudoers that keeps HOME:** `TryHostLock` creates root-owned `firecracker-slot-<i>.lock` files, and possibly the locks dir itself, in the user's cache. The user's next build then fails with "permission denied", because `acquireSlot` returns that error without trying the next slot.
   - **Suggested fix:** under root with `SUDO_USER` set, read that user's pid files without locking, or print `skip` for those rows. Never create lock files as root.
4. **UX-04**, `driver/firecracker/driver_linux.go:154`.
   - **What's wrong:** the slot is taken only after `stage()`, which converts the image and copies the multi-GB rootfs. With every slot busy, a build pays for the copy and then fails. The design's pseudocode takes the slot first.
   - **Suggested fix:** call `acquireSlot` before `deliver()`, or probe for a free slot in preflight.
