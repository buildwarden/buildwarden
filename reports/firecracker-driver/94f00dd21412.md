## `lockAs` review

- **Per-thread switch: correct.** In x/sys v0.47.0, `unix.Setgroups` is a raw `SYS_SETGROUPS` and `setfs[ug]id` are plain syscalls, so only the calling thread changes. Package `syscall`'s Setgroups would have used AllThreadsSyscall.
  - The order is groups, fsgid, fsuid, each set while still privileged. The double call reads each id back.
  - A non-zero fsuid clears the thread's effective fs capabilities, so every check on the path is the user's.
- **No other goroutine on that thread: correct.** `LockOSThread` runs before any switch. A locked M runs only its goroutine, and blocking syscalls keep the M.
  - Threads the runtime needs meanwhile come from the template thread, which `LockOSThread` starts from a root thread. No thread is cloned with the user's creds.
- **Disposal: wrong for the main thread.** See finding 15.
- **Symlinks and TOCTOU: sound.** A link the user plants reaches only what the user could open read-write anyway. No root check comes before the open, so there is no check-then-use gap.
  - The fd is O_CLOEXEC, so setup's `ip` and `nft` children do not inherit it.
- **Error paths: sound.** Every failure returns an error, and `quiesceSlots` releases the locks it already took. Lock files it created stay behind, owned by the user, exactly as a build would leave them.
- **Warden's other threads stay root: yes, for every thread that runs Go code.** The probe confirmed it.

15. **GLOBAL-06** (GLOBAL-01, GLOBAL-04), `driver/firecracker/slots_linux.go:148`. *New.*
   - **What's wrong:** the comment says the runtime discards the never-unlocked thread. That is false for m0.
     - When a locked goroutine exits on the main thread, `runtime.mexit` parks the main thread for good ("Just wedge it") rather than exit it.
     - The goroutine is queued as the caller's `runnext`, so it runs on the caller's M. In warden the caller is setup on the main goroutine, so the first call lands on m0 in practice.
     - Observed as root under WSL, 5 runs out of 5: after the calls, `/proc/self/status` (the thread-group leader) reads `Uid: 0 0 0 65534` and `Groups: 65534`, while every other live thread reads 0.
   - **Impact is low, and the boundary holds:**
     - The wedged thread never runs Go code again (the runtime throws if it wakes). Signal handlers may still run on it, but they do no path lookups.
     - The kernel's ptrace and kill checks use the target's uid, euid and suid, which stay 0. The build user gains nothing.
   - **Still worth fixing:** the shipped safety argument is wrong, and a root process shows the build user's identity to `ps` and anything else that reads its status. `TestLockAsUsesUserCreds`'s "stays root" check samples one thread, so it cannot catch this.
   - Also, any fsuid change resets the process's dumpable flag to `suid_dumpable`. Setup is non-dumpable after its first `lockAs`. That is harmless here.
   - **Suggested fix:**
     - Before the goroutine returns (success or failure), restore root's fsuid, fsgid and the groups `unix.Getgroups` read before the switch, each read back. Keep the thread locked.
     - Fix the comment.
     - Make the root test read every `/proc/self/task/*/status` and require fsuid and fsgid 0 and root's groups on every task. That test fails today.
16. **GLOBAL-06** (UX-04, FLOW-06), `docs/design/firecracker-driver.md:1232`. *New: the residuals of finding 13.*
   - **What's wrong:** both stated residuals are accurate and, as documented, acceptable for Jeff to sign off. They belong in the PR's security note.
     - **`XDG_CACHE_HOME`:** default sudo `env_reset` drops it, so a user whose builds use a non-default cache dir has setup hold locks no build takes.
       - The carrier check still finds running VMs. What is lost is a build that starts during setup's seconds-long run.
       - The drivers guide (`drivers.md:390-395`) tells such users to start no build while setup runs.
       - The root-owned setup gate would close this. Leaving it out is a defensible trade.
     - **`slots.sh`:** it checks carrier and held locks but holds none through the reload. It is the documented debugging stand-in, and its comment says so.
     - Two small points in its new lock check (`slots.sh:134-141`):
       - It reads only `~/.cache`, the same residual as above.
       - Root opens a user path between `[ -f ]` and `9<`. If the user swaps in a FIFO in that gap, root's script hangs. A symlink only makes root open a file read-only, which is harmless. The case is the owner's own doing, and low.
   - **Suggested fix:**
     - Carry both residuals into the PR body's security note.
     - In `slots.sh`, run the check as the user, mirroring `lockAs`: `runuser -u "$user" -- flock -n "$f" true`.
     - Take the setup gate later only if a user reports the `XDG_CACHE_HOME` case.
