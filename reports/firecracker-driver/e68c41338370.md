## Review of b748c1a (`lockAs` restore)

- **Restore order: correct.** `restore` sets fsuid first, then fsgid, then groups.
  - Setting fsuid back to 0 makes the kernel raise the fs capabilities again from the permitted set. A non-zero fsuid never drops `CAP_SETUID` or `CAP_SETGID`, so the fsgid and setgroups calls that follow are still privileged.
  - Each id is read back: setfs[ug]id by its double call, groups by `Getgroups` plus `slices.Equal`. The kernel sorts the group list on setgroups, so the list read before the switch compares equal after the restore. With no groups, both sides are nil.
- **Every path restores: correct.**
  - `restore` is returned on each `switchCreds` failure, and `lockAs` calls it unconditionally. A partial switch (groups set, fsgid failed) is undone.
  - A warden already running as the user gets a no-op restore. A `Getgroups` failure before the switch also gets a no-op, which is correct because nothing has changed yet.
- **Unlock only after a verified restore: correct.**
  - `UnlockOSThread` runs only when `restore` returns nil.
  - On failure, the open file is closed (close makes no permission check) and the joined error is returned, so `quiesceSlots` fails and releases what it holds.
  - A thread that cannot be restored stays locked. Its uid, euid and suid stay 0, as the comment and the design note now say.
- **Snapshot of the old ids: correct.** It takes `os.Geteuid()`/`os.Getegid()` as the prior fsuid/fsgid, which holds because nothing else in warden changes fs ids. It reads the prior groups on the locked thread itself.
- **Comment and design note: accurate.** They now describe the m0 park. The design note's paragraph cites f4 report 94f00dd, finding 15.
- **Test: adequate.** `allTasksRoot` reads every `/proc/self/task/*/status` before and after 20 relocks. It requires `Uid`/`Gid` to be `0 0 0 0` and root's groups, and skips tasks that exit while being read.
  - Nit, not a finding: `relock`'s comment says a call "leaves [a thread] locked". After this fix a successful call leaves no thread locked. The 20 calls are still a sound regression check: before the fix they wedged m0 with the user's ids, and now every thread must read root's. Reword the comment if the file is touched again.

## Review of e68c413 (`slots.sh`)

- `runuser -u "$user" -- flock -n "$f" true` opens the lock as the owner, with initgroups, mirroring `lockAs`. Root opens no path in the user's dir.
