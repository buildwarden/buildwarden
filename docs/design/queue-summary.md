# QUEUE.md: a generated summary of the queue

## Problem

The queue state is one YAML file per feature on the `workflow` branch. To see
what is active, at which phase, what is in the backlog and, above all, what
waits on Jeff, he has to run `wf status` from a checkout or read every file.
The daily digest says what moved, not where everything stands. Jeff asked for a
concise Markdown view on the branch itself, readable on GitHub.

## Prior art

- `workflow-bootstrap.md` put the queue on the orphan `workflow` branch and
  gave `wf status` a tab-separated listing for agents.
- `workflow-streamline.md` reduced the human's touchpoints to questions, the
  design review and the merge; those are what the summary must surface first.

## Decisions

1. **Generated by `wf`, in Go, not by a separate script.** `wf` already parses
   and validates the queue, so the summary cannot drift from the schema, and it
   builds wherever Go does, the Windows native host included (GLOBAL-07).
   Rejected: a Python script (a second YAML parser, plus Python and PyYAML on
   every machine).
2. **Rewritten whenever `wf` writes state, and by `wf validate`.** Every
   command that saves a queue file also rewrites `QUEUE.md`, and `wf validate`
   (which every agent runs after editing a queue file by hand) does too, so the
   file is committed with the state change that produced it. Rejected: a git
   pre-push hook (hooks are not versioned, so a fresh clone, the cloud loop and
   the native machines would not have it, and the file would go stale).
3. **Deterministic.** The "updated" time is the newest history event across the
   queue, not the wall clock, so regenerating unchanged state changes nothing
   and tests need no clock.
4. **`wf status -md`** prints the same Markdown to stdout.

## Design

`queue.Summary(s *State) string` renders, in order:

1. `# Queue` with the updated time.
2. **Needs Jeff**: open blocking questions; ready `human` steps (design reviews,
   answers, escalations); features waiting for his merge (feature phase 7,
   process phase 3, with the PR number); runaway budgets (FLOW-13). "Nothing"
   when empty.
3. **Active**: in-progress items in FLOW-05 order: priority, feature, phase,
   the next pending steps with affinity and any live lease, spent against
   estimated steps. Process items show what they hold.
4. **Waiting on a host**: pending `host:<name>` steps, when there are any.
5. **Backlog**: queued items in FLOW-05 order: priority, feature, kind,
   estimated steps.
6. **Recently done**: items done within 7 days of the updated time, with the
   PR number and date.

`State.WriteSummary()` writes it to `<dir>/QUEUE.md`. `State.Save` calls it
after writing the feature file, and `wf validate` calls it after a clean
validation. The `workflow` branch's `README.md` lists `QUEUE.md` in its layout
table.

## Validation plan

Tier 0 (TEST-01): a golden test renders a fixed state covering every section
(a blocking question, a design review, a PR waiting, a runaway, a host step,
queued items, a done item inside and outside the 7 days) and compares it with
`testdata/queue.md`; a test that `Save` writes `QUEUE.md`; a test that
rendering the same state twice is identical. Then a dry run on a copy of the
live `workflow` branch.

## Implementation plan

1. `queue/summary.go`: `Summary` and `WriteSummary` (FLOW-03, FLOW-05,
   FLOW-13, FLOW-19).
2. `State.Save` and `wf validate` write it; `wf status -md` prints it
   (FLOW-14).
3. Golden and determinism tests (TEST-01).
4. The `workflow` branch's README layout row, and the first generated
   `QUEUE.md`, after merge (FLOW-03).
